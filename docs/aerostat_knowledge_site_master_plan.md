## 0. 文档定位

本文档用于替代旧版本地部署计划，作为当前阶段的**总路线备案文件**。  
目标不是描述一个理想化的“最终平台”，而是结合目前已经实际搭建完成的环境，形成一份**可执行、可验收、可回滚、可对外说明**的开发总方案。

本文档强调五个原则：

1. **以当前真实环境为起点，不重走已经完成的步骤**
2. **优先完成最小闭环，而不是堆叠过多技术名词**
3. **优先形成一个可展示、可灰测、可解释的原型系统**
4. **所有核心开发统一在 WSL2 Ubuntu 环境内完成**
5. **每一阶段都要有明确验收标准与回滚点**

## 2. 本项目的目标定义

### 2.1 核心目标

在现有本地设备上，完成一个可演示的“浮空器领域知识网站”原型系统，形成如下最小闭环：

```text
资料导入
  ↓
文本抽取 / 切分
  ↓
向量化 / 索引
  ↓
问题输入
  ↓
检索相关片段
  ↓
生成回答
  ↓
展示来源与引用
```

### 2.2 原型阶段希望达到的能力

第一版原型至少应满足：

- 网页可访问
- 文档可进入系统
- 文档状态可见
- 可进行提问
- 可返回相关答案
- 可显示来源信息
- 可体现“浮空器领域”特化方向

### 2.3 当前阶段不追求的内容

以下内容明确后置：

- 用户注册 / 登录系统
- 权限管理与多租户
- 公网正式部署
- 高并发访问
- 复杂 Agent 工作流
- GraphRAG
- 重型 OCR / VLM 主链路
- 本地大模型作为核心依赖
- 完整监控告警平台
- 生产级灾备与自动化运维

## 3. 修订后的总体技术路线

### 3.1 目标架构（本地原型版）

```text
A端 WSL2 Ubuntu
├── frontend（React + Vite）
├── backend（FastAPI）
├── qdrant（向量库）
├── sqlite（初期元数据存储）
├── local docs storage（本地资料目录）
└── 可选：后续接入 PostgreSQL / MinIO
```

### 3.2 技术选型结论

#### 前端

推荐：**React + Vite**

原因：

- 启动快
- 结构轻
- 足够支撑原型演示
- 比 Next.js 更适合快速起步

#### 后端

推荐：**FastAPI**

原因：

- 文档完善
- API 开发快
- 对 Python 生态友好
- 后续上云迁移成本较低

#### 向量库

推荐：**Qdrant**

原因：

- Docker 启动简单
- 本地原型验证足够稳定
- Dashboard 可辅助调试

#### 元数据数据库

当前推荐顺序：

1. **SQLite 起步**
2. **后续再升级 PostgreSQL**

原因：

- 第一版重点是闭环，不是复杂事务场景
- SQLite 足以支撑单人原型阶段文档状态与元数据管理
- 后续需要更完整的查询与迁移时，再切 PostgreSQL

#### 模型调用策略

原型阶段建议：

- 问答模型：优先 API
- Embedding：优先 API 或轻量模型
- 本地模型：只做可选尝试，不作为主链路依赖

原因：

- 当前 16GB 内存与 3050 Laptop GPU 适合验证，不适合过早重压本地模型
- 你的核心目标是做出平台原型，而不是先把模型栈做满

## 4. 当前项目目录与推荐组织方式

### 4.1 顶层目录建议

建议在 `~/workspace` 下建立正式项目：

```text
~/workspace/aerostat-knowledge-site/
├── frontend/
├── backend/
├── docs/
├── infra/
└── scripts/
```

### 4.2 目录说明

#### `frontend/`

放置前端代码：

- React + Vite 页面
- 基础 UI 组件
- 首页 / 知识库页 / 问答页

#### `backend/`

放置后端代码：

- FastAPI 服务
- 上传、索引、问答 API
- 文档状态管理
- Qdrant 调用逻辑

#### `docs/`

放置项目文档：

- 术语表
- 设计说明
- 演示问题
- 灰测记录
- 部署说明

#### `infra/`

放置基础设施文件：

- `compose.yaml`
- `.env.example`
- 服务初始化脚本
- 开发环境配置

#### `scripts/`

放置常用辅助脚本：

- 启动脚本
- 导入文档脚本
- 初始化 Qdrant 集合脚本
- 本地测试脚本

### 4.3 数据目录建议

系统运行时持久化数据统一放在：

```text
~/data/
├── docs_raw/
├── docs_processed/
├── qdrant/
├── sqlite/
└── exports/
```

含义如下：

- `docs_raw/`：原始资料
- `docs_processed/`：抽取与切分后的中间结果
- `qdrant/`：向量库持久化数据
- `sqlite/`：SQLite 数据文件
- `exports/`：阶段性导出与备份

## 阶段 4：接入 Qdrant，跑通最小 RAG 链路

### 4.1 阶段目标

完成从文档到检索结果的最小闭环。

### 4.2 标准流程

```text
原始文档
  ↓
文本抽取
  ↓
chunk 切分
  ↓
embedding
  ↓
写入 Qdrant
  ↓
问题向量化
  ↓
相似度检索
  ↓
返回相关片段
```

### 4.3 本阶段约束

- 文档数：3～5 份起步
- 文档内容：优先可直接抽取文本的资料
- 不做复杂 OCR
- 不做多文档复杂综合问答

### 4.4 验收标准

- 至少 1 份文档可被切分并索引
- 提问时可返回相关文本块
- 基础日志可看出流程是否成功

## 阶段 5：问答与来源展示

### 5.1 阶段目标

### 5.2 本阶段内容

- 返回回答正文

- 回答页面不是只显示原始 chunk

- 对单文档事实问题有基本可用效果

## 9. 风险与避坑建议（结合当前实际环境）

### 9.1 不要把开发环境再混回 Windows

所有核心开发应继续放在 A 端 WSL 内进行。

### 9.2 不要一开始就引入太多服务

第一版不要急着上：

- PostgreSQL
- MinIO
- 本地大模型主链路
- 复杂任务队列
- 监控平台

### 9.3 代理配置要有“显式落地”

当前已经验证过：

- WSL 自动代理
- Docker daemon 代理
- SSH / VS Code 远端会话代理

后续任何新增服务，如果涉及出网下载，优先检查是否正确继承代理。

### 9.4 Docker 只做服务，不要把所有开发都包进容器

建议：

- 前端开发服务器：先在 WSL 内直接跑
- FastAPI 开发服务器：先在 WSL 内直接跑
- Qdrant / 后续数据库：用 Docker 跑

这样便于快速调试。

### 9.5 原型阶段尽量少碰重型 PDF

优先选择：

- 综述摘要
- 术语表
- 教材片段
- 文字型论文资料

避免把大量扫描版 PDF 在第一阶段引入。
